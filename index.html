Understanding ColBERT's Query and Document Encoders

September 15, 2026 · 10 min read

1. Introduction

Before ColBERT can compare a query against a document, it first needs to convert them into vectors, basically into numbers that a machine can compare. The way ColBERT does this conversion matters a lot, as the late interaction step depends on it. If it is not properly done, the final comparison won't be good either.

ColBERT does this with two encoders, a query encoder and a document encoder. Both are built on top of BERT. There are many similarities in their working, but each encoder treats its inputs slightly differently. These small differences are important because they affect how ColBERT represents and compares queries and documents.

This article walks through exactly how each encoder works, why query augmentation exists, and why the final embeddings are normalized to unit length.

2. One BERT, Two Jobs

ColBERT turns each query and each document into a collection of embeddings before the late interaction step ever happens. Instead of using two separate models for this, it uses the same BERT model for both queries and documents. To tell BERT what kind of input it's processing, ColBERT adds a special token right after the [CLS] token. That token is [Q] for queries and [D] for documents.

By using the same BERT model and adding a marker token to distinguish between queries and documents, ColBERT can keep both embeddings consistent with each other while still allowing the model to treat them differently.

3. The Query Encoder

The query encoder first breaks the query into BERT's WordPiece tokens. Then it inserts a special [Q] token immediately after BERT's [CLS] token, telling BERT this is a query input.

ColBERT makes every query the same length, Nq. If the query is shorter than that, ColBERT adds [mask] tokens until it reaches Nq. And if the query is longer than that, ColBERT keeps the first Nq tokens. This final sequence is then passed through BERT, which produces a contextualized representation for every token in it.

3.1 Query Augmentation

Padding a query with [mask] tokens might seem like a small technical detail, but it has a really important purpose. The ColBERT paper calls this query augmentation. Instead of leaving those extra positions empty, the [mask] tokens give BERT additional positions where it can produce contextualized, query-based embeddings.

In simple words, it gives the model a way to expand the query with new terms or re-weight the importance of existing ones, without anyone hand-engineering that expansion. The [mask] tokens effectively become extra "slots" where the model can learn to create new query related embeddings which helps to find relevant documents.

4. The Linear Projection Layer

BERT creates a contextualized vector for every token. ColBERT then passes each of these vectors through a linear layer, which reduces BERT's original representation into a smaller, m-dimensional embedding. For example, BERT might produce a 768-dimensional vector, and the linear layer compresses that into something like a 128-dimensional one.

Normally, after a linear layer, a neural network adds an activation function, for example ReLU, to filter or reshape the output. ColBERT does not follow this approach. There's no activation function used here. The linear layer's final output is used directly as the embedding.

5. Embedding Dimension, Storage, and Query Latency

m denotes how many numbers make one embedding, just like how a 3D point is three numbers. ColBERT keeps this embedding small, typically around 128, even though BERT's own vectors are 768 numbers wide. The linear layer reduces them down to smaller numbers while keeping the important information needed for matching.

On the query side, this does not make much difference. A query only contains a few tokens, and encoding them is fast no matter how big m is.

Documents are where the embedding size really matters. ColBERT stores one embedding per token, and a real collection contains millions of documents, each document with dozens to hundreds of tokens. Storage is directly proportional to m. The larger the embedding size, the more storage ColBERT needs. If we double m, the index will also roughly double in size. That's why ColBERT keeps m small. It's not to improve accuracy, but to reduce storage.

The large size of m also makes the queries slower. ColBERT stores the embeddings in CPU memory as they could not fit into the GPU because of their huge size. Therefore, ColBERT first needs to move the relevant document embeddings from the CPU to the GPU at the time of scoring the query. And this transfer of data can take more time than the actual scoring, which makes it the slowest part of ColBERT's re-ranking.

6. Normalization: Turning Dot Products into Cosine Similarity

Once the embeddings are created, ColBERT normalizes each one so its vector length (L2 norm) equals 1. After this, the size of its values does not matter. ColBERT only depends on the direction of the vector.

Since both the query and document embeddings have length 1 after normalization, their dot product will be mathematically identical to their cosine similarity. That means instead of running a separate cosine similarity calculation, ColBERT can just compute a plain dot product, which makes the operation much cheaper. And the resulting similarity score ranges between -1 and 1.

7. The Document Encoder

The document encoder works almost exactly like the query encoder. ColBERT splits the document into its individual tokens, then it adds [CLS] followed by the special [D] token at the beginning to tell BERT that it is a document input, not a query input.

Unlike queries, ColBERT doesn't pad documents with [mask] tokens. It only uses query augmentation on the query side.

ColBERT then passes this resulting sequence through BERT, and then the same linear layer is used to produce an embedding for each token. After that, ColBERT does one more thing that it doesn't do for queries. It removes the embeddings corresponding to punctuation marks, using a predefined list of punctuation tokens, to reduce the number of embeddings stored per document.

The reasoning behind this is a hypothesis. It's not a proven fact. The authors assume that punctuation embeddings don't contribute meaningfully to retrieval effectiveness, even though they're contextualized like everything else, so they remove these embeddings to save storage space.

8. Putting It All Together

Given a query q = q₀q₁...ql and a document d = d₀d₁...dn, ColBERT turns them into two bags of embeddings Eq and Ed as follows. Here, # represents the [mask] tokens. One important note before you read them. Here, CNN is just the paper's label for the linear projection layer from Section 4. This is not a convolutional neural network. There's no convolution happening anywhere in this pipeline.

Eq := Normalize( CNN( BERT( “[Q]q0q1...ql##...#” ) ) )

(1)

Ed := Filter( Normalize( CNN( BERT( “[D]d0d1...dn” ) ) ) )

(2)

These two equations are really just a compact way of summarizing everything above. For a query, ColBERT adds the [Q] token and [mask] padding, passes everything through BERT, sends it through the linear projection layer (written as CNN in the equation), and normalizes the resulting embeddings to get Eq. For a document, it adds [D], passes it through BERT and the same linear projection layer, normalizes it, and removes the punctuation embeddings to arrive at Ed.

9. Conclusion

None of the encoders does anything fancy on its own. The basic flow is pretty simple. ColBERT tokenizes the text, adds a special token to mark the input type, runs it through BERT, passes it down with a linear layer, and then normalizes it.

What makes the design interesting is how the two encoders differ. The query augmentation adds extra [mask] tokens, while the document side filters out punctuation. There is a fixed length for queries, while the documents can have variable lengths.

Each of these choices comes from the same trade-off ColBERT is built around. Keep documents cheap to store and index offline, while giving queries just enough flexibility at search time to make late interaction work effectively.
