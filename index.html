Understanding ColBERT's Query and Document Encoders

September 9, 2026 · 10 min read

1. Introduction

Before ColBERT can compare a query against a document, it has to turn both of them into something a machine can actually compare: vectors. How it does this conversion turns out to matter a lot. Get it wrong, and the late interaction mechanism sitting on top has nothing good to work with.

ColBERT handles this with two encoders, a query encoder and a document encoder, both built on top of BERT. They share the same underlying model but treat their inputs a little differently, and those small differences are where most of the interesting design decisions live.

This post walks through exactly how each encoder works, why query augmentation exists, and why the final embeddings end up normalized to unit length.

2. One BERT, Two Jobs

ColBERT converts each query and each document into a set, or "bag," of embeddings before the late interaction step ever happens. Instead of training two separate models for this, it uses the same BERT model for both queries and documents. What tells BERT which kind of input it's looking at is a special token prepended at the very start: [Q] for queries and [D] for documents.

That single design choice, sharing weights and distinguishing inputs with a marker token, is what keeps the two encoders consistent with each other while still letting them behave differently downstream.

3. The Query Encoder

The query encoder starts by breaking the query into BERT's WordPiece tokens. It then inserts the [Q] token immediately after BERT's [CLS] token, marking the input as a query.

Queries are forced into a fixed length, Nq. If the query is shorter than that, ColBERT pads it out with [mask] tokens. If it's longer, only the first Nq tokens are kept. This padded sequence is what actually gets passed through BERT, which produces a contextualized representation for every token in it.

3.1 Query Augmentation

Padding a query with [mask] tokens sounds like a minor implementation detail, but it's actually doing real work. This is what the ColBERT paper calls query augmentation, and it lets BERT produce query-based embeddings at those masked positions rather than leaving them empty.

Functionally, it gives the model a soft, differentiable way to expand the query with new terms or re-weight the importance of existing ones, without anyone hand-engineering that expansion. The masks effectively become extra "slots" the model can fill with whatever it thinks is relevant to matching the query.

4. The Linear Projection Layer

BERT itself produces a contextualized vector for every token. ColBERT then passes each of these vectors through a linear layer, which projects BERT's original representation down into a smaller, m-dimensional embedding. BERT, for example, might output a 768-dimensional vector, and the linear layer compresses that into something like a 128-dimensional one.

Normally, a network might follow a linear layer with an activation function, ReLU being the obvious example, to filter or reshape the output. ColBERT skips that step entirely. There's no activation here: the linear layer's raw output is used directly as the embedding.

5. Embedding Dimension, Storage, and Query Latency

m is just how many numbers make up one embedding, the same way a 3D point is three numbers. ColBERT keeps it small, around 128, even though BERT's own vectors are 768 numbers wide, and that's what the linear layer shrinks them down to.

On the query side this barely matters. A query is only a handful of tokens, so encoding them is fast no matter how big m is.

Documents are where it counts. ColBERT stores one embedding per token, and a real collection has millions of documents with hundreds of tokens each. Storage scales directly with m: double it, and the index roughly doubles in size. That's why m stays small: not for accuracy, but for storage.

It slows queries down too. Document embeddings live off the GPU, in CPU memory, since there are too many to keep loaded. So scoring a query means first pulling the right embeddings off the CPU and shipping them to the GPU, and that transfer, not the actual scoring, is often the slowest part of ColBERT's re-ranking.

6. Normalization: Turning Dot Products into Cosine Similarity

Once the embeddings are produced, ColBERT normalizes each one so its L2 norm, its vector length, equals 1. This makes direction the only thing that matters about an embedding, not magnitude.

Because both the query and document embeddings have length 1 after normalization, their dot product ends up being mathematically identical to their cosine similarity. That means ColBERT can just compute a plain dot product instead of running a separate cosine similarity calculation, which is a much cheaper operation. The resulting similarity score falls somewhere between -1 and 1.

7. The Document Encoder

The document encoder mirrors the query encoder almost exactly. ColBERT breaks the document into its individual tokens, then prepends [CLS] followed by the special [D] token to mark the sequence as a document rather than a query.

One notable difference: documents are never padded with [mask] tokens the way queries are. There's no query augmentation equivalent on the document side.

The resulting sequence is passed through BERT and then the same linear layer used elsewhere, producing an embedding for each token. After that, ColBERT does one more thing that queries don't get: it strips out the embeddings corresponding to punctuation marks, using a predefined list of punctuation tokens, to cut down on how many embeddings need to be stored per document.

The reasoning behind this is a hypothesis rather than a proven fact: the authors believe punctuation embeddings, even though they're contextualized like everything else, don't contribute meaningfully to retrieval effectiveness, so there's little reason to pay the storage cost of keeping them around.

8. Putting It All Together

Given a query q = q₀q₁...ql and a document d = d₀d₁...dn, ColBERT computes the bags of embeddings Eq and Ed as follows, where # denotes the [mask] tokens. One notation note before you read them: CNN here is just the paper's label for the linear projection layer from Section 4, not a convolutional neural network. There's no convolution happening anywhere in this pipeline.

Eq := Normalize( CNN( BERT( “[Q]q0q1...ql##...#” ) ) )

(1)

Ed := Filter( Normalize( CNN( BERT( “[D]d0d1...dn” ) ) ) )

(2)

These two equations are really just a compact restatement of everything above. For a query, ColBERT adds the [Q] token and [mask] padding, runs everything through BERT, passes it through the linear projection layer (written as CNN in the equation), and normalizes the result to get Eq. For a document, it adds [D], runs it through BERT and the same linear projection layer, normalizes it, and then filters out the punctuation embeddings to arrive at Ed.

9. Conclusion

Neither encoder does anything exotic on its own. Tokenize, mark the input type, run it through BERT, project it down with a linear layer, normalize it. What makes the design interesting is the handful of asymmetries between the two: query augmentation on one side, punctuation filtering on the other, a fixed length for queries versus a variable one for documents.

Each of these choices exists for a reason grounded in the trade-off ColBERT is built around: keep documents cheap to store and index offline, while giving queries just enough flexibility at inference time to make late interaction actually work.
